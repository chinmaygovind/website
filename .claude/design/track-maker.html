The shape of it

A user track is one row: a name, an author, a JSON list of moves, a JSON palette, a status. Loading one means replaying its moves through tracks/builder.py — the same turtle that builds Spa — and handing the result to the same _one() that derives medals, pole side, gate ceiling and the ideal lap.

So a player's track is not a second kind of track. It is the same dict, assembled from a different document.

load pathone code path, two documents
# the pool, today
tracks/spa/track.py   → build(b) → Builder → ribbon → _one() → track dict
                            ↑
# a player's track, new
drive_user_tracks row → replay(moves) ────┘

both end up in tracks.get(slug) — and that is called from 20+ places in
app.py: /solo, /api/track, /api/run, /api/start, /api/ghost, rooms,
replays, share cards, robots.txt, sitemap.xml, the switcher.

Teach tracks.get to resolve a live user slug and every one of those routes works with no further change. That is the whole trick, and it is why this is a small feature rather than a second game.

What never crosses the wire

No user Python, ever. User JavaScript runs in exactly one place: a sandbox in the editor, while the author is looking at it. It never runs on a path that matters. The three paths that made me say no at first — inlined into the play page, fetched by the switcher, bundled into the QuickJS anti-cheat — all consume baked geometry, not code. See Scenery in code below for how.

Everything else rides the same rails the palette does: _track_payload sends the track dict to the page and jsrt sends it to QuickJS, so data on the dict reaches the browser and the anti-cheat with no new plumbing.

The moves document

A correction to what I told you first. I said Builder.sections already maps onto an editor, because of its “authored primitives, in order — for an editor” comment. It doesn't. width(), rail() and bank() append nothing; crest() records itself as an ordinary straight, so a jump and a hill are indistinguishable in it; and checkpoints live in gates, never in sections. It is a lossy positional index built for the closure solver. The editor needs its own complete schema, and sections stays exactly what it is.

One deliberate difference from the turtle: every move carries its own width, edges and bank rather than inheriting sticky state. In a text file b.width(13) reads fine; in a list you can reorder, deleting one move silently rewidens nine others. The replayer converts declarative back to sticky by calling b.width() / b.rail() / b.bank() before each move when the value changes.

Five shapes to start from decided

Sprint, Circuit, Mountain Climb, Stunt Park, Blank. Each is a short, real, drivable track with a matching palette — so the first thing anyone can do is press Drive, and every control on screen is already demonstrated by something in the list. I'd author these as ordinary rows and seed them, which means they are editable by you without a deploy.

Circuit is the one to build first and the one to watch: it sets closed = true, so it pays solver.close() and can refuse. A player who drags a straight from 90 to 40 will break closure, and the editor has to say “this lap no longer meets itself, and I can stretch it 15% at most” rather than failing at save.

The look, and the ceiling

You overrode my concern here, so: every palette key, exposed, for everyone. look.check already makes the two silent failures impossible — a missing required key can't ship, and a misspelled optional one is refused rather than ignored. What's left is taste, and taste gets warnings, not walls.

Two things make that work rather than just be permissive. First, nobody starts from a colour wheel: a new track arrives with a real palette from its starting shape, and a fork arrives with the palette of whatever it forked. Second, the preview is from the driver's seat, in motion, because your own log says a night palette can be beautiful in a still and unreadable at speed.

Every warning below is already written down in docs/track-defects.md or measurable by tools/pool_stats.py. The editor is just the first place they get said to the person who caused them.

The honest answer to “as beautiful as mine”. With scenery as data (next section), a player can reach seventeen of your nineteen. Fourteen are a track.py and a palette.py and nothing else. Spa joins them, because its grandstands, pits, gantry, flags and hoardings are already a data block. Silverstone and Tokyo Drift join them too — hangars, a roof over the pits, city towers and two inside barriers are all placements, not shapes. What stays out is Costco, which puts solid geometry over the road, and Mount Joy and Shroom Street, which sculpt their own height fields. Those three are genuinely code — and with code mode a determined player can now reach a good deal of even those, which is the strongest argument for having it.

Forking one of the three copies its moves and everything expressible, and drops building, shore and rainbow* with a line saying so. terrain and furniture both stay — both are data, both derived off the ribbon, both survive a layout change by construction.

Scenery, without code

Read the five hand-written scenery.js files next to each other and they are the same file five times. Every one opens by defining the same four helpers, and then spends three hundred lines using only those:

  • at(f) — a fraction of the lap becomes a station index
  • spot(i, o) — a world point o units to the road's right at station i
  • ground(i, o) — the height there, road-minus-drop inside the apron and the height field beyond it
  • face(a,b,c,d) — a quad drawn both windings, because MeshLambertMaterial is FrontSide and a mirrored side reverses the winding

So the entire spatial grammar of every building on this game is three words: at, side, off. Silverstone's load-bearing barrier — the only part of that file the stopwatch can see — is already written as insideBarrier(0.122, 0.203). Spa's entire trackside is already a data block.

So: a player's scenery is a list of placements, and the interpreter is one engine-owned props(ctx) — a sixth implementation of the contract the five already share, driven by data instead of by hand.

Six defects stop being possible

This is the part that makes the declarative path better than a hand-written file rather than merely safer. Each of these is a live entry in docs/track-defects.md currently looked for by eye, and each becomes structurally unreachable when the interpreter owns the helpers:

  • ✓Hand-placed geometry that does not move when the road does. There is no way to write a world coordinate. Every placement is a fraction of the lap.
  • ✓A quad wound the wrong way is invisible, and nothing says so. Users never write quads; face() draws both.
  • ✓Geometry floating in the sky. Everything stands on ground(i, o).
  • ✓Scenery standing on nothing past the edge of the ground. The interpreter clamps to the plate and insets by the object's own footprint.
  • ✓A scenery.js that throws can leave the suite green. Data does not throw, and look.check-style key validation refuses a typo rather than ignoring it.
  • ✓The collider is missing on one path and nowhere else. One interpreter, reached identically by the page, the switcher and QuickJS. There is no per-path copy to miss.

A seventh comes free: stand already refuses to build where another part of the lap is, using the same nearest-road test the armco and the run-off use. Every object in the list inherits that, so a player cannot lay a grandstand across a corner further round the lap — which is a thing that happened to La Source.

The one that moves the stopwatch

wall is collider geometry (KIND.WALL), so it is the only object here a lap time can feel, and it is the one worth having: it is how Silverstone kills the cut across Luffield, and a ribbon rail is not available on a ground track. Three consequences, all of them already handled by decisions you have made:

  • It reaches the anti-cheat automatically, because the placement list rides the track dict exactly as the palette does.
  • tools/cut_check.py asks the collider, not the plan, so it sees a player's wall the same way it sees Silverstone's.
  • A wall laid across the road makes the track unfinishable — and the clean-lap gate you chose catches that empirically, before it can ever reach your queue.

What stays out of v1, and why

An interior with a roof over the road. Costco is one worked example, not a general rule: it sets gate_ceil to its full 14, needs the chase camera's 4.3-up and 11.6-behind cleared at every opening, and forced SHELL_CEIL and DECK to move together. That is a set of couplings to get right per track, and getting it wrong is a camera through a lintel rather than a warning.

Sculpted height fields. Mount Joy's lower-envelope-of-cones and Shroom Street's excluded-station field are each a different rule, invented for one track. pal.terrain stays available; carving does not.

Uploads of any kind. A hoarding takes 24 characters of plain text, filtered, painted by the fallback painter that already exists for a name not in SPONSORS. No image, no SVG, no logo — a board is a billboard on your domain, and the only safe version of that is type.

Scenery in code

Nine objects cover most tracks. Code is for when they don't — and it is the same ctx the built-in objects are implemented against, so a player writing scenery and the engine drawing a grandstand are using one API.

The rule that makes this safe is one sentence: code runs while you author, geometry ships. Untrusted JavaScript executes only in a sandbox in the editor. On submit, the geometry is baked to numbers and it is the numbers that go live — so the play page, the switcher and the QuickJS verifier never run a stranger's code.

authoring→ submit → production
# in the editor, on every keystroke

                  no same-origin fetch, no storage)
                  → Worker + three_stub.js → postMessage

The worker needs no three.js: three_stub.js already exists because the anti-cheat runs trackmesh.js headless, so the geometry code runs with the stub the verifier already uses. A timeout terminates the worker; a runaway loop costs the author a second and nobody else anything.

The one real vulnerability, and its fix

KIND in trackmesh.js is {ROAD: 0, WALL: 1, OFFROAD: 2, BOOST: 3, BOUNCE: 4}. A player's scenery may emit WALL and OFFROAD, and nothing else, and that is not tidiness — it is the whole security boundary.

A user-emitted BOOST quad would be a boost pad baked into the track, and the verifier re-drives submitted laps against that same collider — so it would be a speed hack that comes with a certificate of authenticity. BOUNCE is the same trick with a trampoline. ROAD is worse in a quieter way: fake road the ground probe picks up, which is a floating surface the car drives on with no ribbon under it. Whitelist on the way in, at the validator, on numbers — never on trust in the code that produced them.

Budgets, from the pool's own numbers

test_scenery.py pins every track's collider: the pool runs 534 to 13,188 triangles total, with wall counts from 100 (Chicane Park) to 2,020 (The Gauntlet). So:

  • Collider: 2,500 triangles. More than the busiest track in the pool.
  • Mesh: 20,000 triangles. Tokyo Drift's city is the shape of thing this has to fit.
  • Bake: 2 seconds, hard. Terminate and report; the author fixes it.
  • Buffer: 150KB gzipped, quantised positions, written to static/user-scenery/<slug>.bin and served by nginx off disk under the $static_expires map that already exists. This is the number that protects the single eventlet worker relaying race poses at 30Hz — the same reason you moved static/ to nginx and went from 1.90MB to 0.47MB on the wire.

What a baked buffer does to the lifecycle

test_scenery.py already states the rule in its own failure message: “the collider changed. Every time on this track's board was driven against the old one.” So the baked collider goes into the geometry hash, and the lifecycle follows without a new rule:

  • Collider changed → board and ghosts wiped, back to the queue. Same as moving a corner, for the same reason.
  • Mesh only → board intact, but still re-queued. Not because lap times care — they don't — but because you approved a particular city, and a mesh-only edit could swap it for something you would not have approved.

The trade to accept out loud: baked geometry does not follow a re-solved ribbon. That is fine here and only here, because a geometry edit already re-queues and re-bakes, and during authoring the code re-runs on every change. It would not be fine if live tracks were editable in place.

One improvement this makes to your existing code

Put at, spot, ground and face on ctx for the sandbox, and all five hand-written scenery.js files get to delete their copies. That removes five independent chances to get face's double winding wrong — the trap that made Spa's pit building an invisible shed with a roof floating in the sky, and both of Silverstone's hangars blank grey walls.

Bring your own AI

The failure mode without this is easy to picture: somebody pastes “make me a city” into a chat window and gets back code using THREE.Mesh, document, world coordinates and single-winding quads — none of which exist here. The model has never seen this API. So the deliverable is not a button, it is making the API legible to whatever model the player already has.

Copy API for your AI. The chat panel, and the three things that will bite

A provider picker — Claude, ChatGPT, Gemini — with the key in localStorage and the request going straight from the browser to the provider. Your box never sees a prompt, a token or a bill. Worth saying in exactly those words, given that /api/roll/gemini was removed for being the opposite of this.

  1. Anthropic needs an extra header. A browser-origin call is rejected unless it sends anthropic-dangerous-direct-browser-access: true; without it you get a 401 naming that header. The word is deliberate — it means “anyone with devtools can read this key” — and bring-your-own-key is the documented legitimate use, because the key belongs to the person whose browser it is.
  2. /make needs its own CSP. Three API hosts in connect-src, on that page only. Every other page keeps the frame-ancestors sitelock exactly as it is.
  3. No temperature slider. On claude-opus-5 and claude-sonnet-5, temperature, top_p and top_k are rejected with a 400 — they are gone, not deprecated. Steer with the prompt. And on claude-opus-5 thinking is on by default, with max_tokens capping thinking and reply together, so size it with headroom or the code comes back truncated.

Default to claude-opus-5; offer claude-sonnet-5 and claude-haiku-4-5 as the cheaper picks. Send the model ID the player chose and nothing else clever — the panel is a thin pipe, and every provider-specific quirk you add to it is one you maintain.

Source is public once you approve it

A draft's code is the author's. Publishing publishes the code with it, and the publish screen says so. In an API with no documentation anywhere else, other people's working scenery is the documentation — and it makes a fork mean something, because you can read how the city you just forked was built.

The gate

Structural checks block. Taste warns. And you cannot submit a track you have not driven from the start line to the flag — which is the best of the four options for a reason worth naming: it proves finishability by demonstration rather than by inference, and it pays for itself three times over.

That first lap becomes the track's first record, its first ghost, and the line tools/hotlap.py needs — so a brand-new user track has quick bots that drive properly instead of the relaxed line, and the failure mode your own notes flag (test_every_track_has_a_usable_hot_lap red on the commit that adds a track) never applies to user tracks at all.

Every line is an existing check in tracks/checks.py or drive/tests/. None of it is new logic — it is the same suite, run per-row on demand instead of per-folder at import, with its output written for a person rather than a test runner.

Lifecycle

Four states, and one rule that keeps a leaderboard meaning something: what you approved is what is live.

draft— submit →queued— you drive it →live   ← hide/unhide → hidden

A cosmetic edit — palette, sky, name, cover, difficulty — saves straight onto a live track. The board is untouched, because none of it changes the road.

A geometry edit wipes the board and the ghosts, drops the track back to queued, and hides it until you approve it again.

“Did the geometry change” needs to be a fact, not a guess: hash the built ribbon — stations, gates, spawn — and store it on the row. Comparing the hash rather than the moves means a no-op edit (drag a slider and drag it back) costs nobody their record, and a change that looks cosmetic but moves the road is caught anyway.

One consequence to accept deliberately: a live track's author can't fix a bad corner without losing the board. That is the correct trade — the alternative is somebody's record silently becoming a time on a different road — but the editor should say it in those words on the Edit button, with the lap count in it.

Review, and the shelf

The queue is a list of names with one button each, and after driving, three more. Nothing else on the page — you said it, and it's right: the only judgement that has ever mattered here is whether it's good to drive.

The checks still run and are still stored on the row; they just aren't a thing you read. If a backlog ever makes you want the pictures and the pool deltas, they are one query away and can be a ?detail view later. Not v1.

Approval is also the ELO gate, and that is now load-bearing rather than incidental. Rooms on user tracks are rated, so an unmoderated gallery would let anyone build a twelve-second oval and farm rating on it. Because nothing is raceable until you have driven it yourself, that hole is closed by a decision you already made for a different reason.

Where an approved track appears

Home page and the in-game switcher keep the nineteen first, then a Community row with the author's handle on each card and a link to the full gallery. A user track is served from /solo/<slug> like every other track, so share cards, watch-a-lap links, canonical tags and the sitemap all work with no new routes.

That means one flat slug namespace, which needs the nineteen reserved at creation time, plus a small denylist. It is worth the reservation: the alternative — a /t/<slug> prefix — buys collision safety and costs a second set of every URL-shaped thing in app.py.

Forking decided

Any live track, including all nineteen, gets a Make my own that copies moves and palette into a fresh draft. The row keeps forked_from, and the card reads “↳ based on Spa-Francorchamps” forever. This is the single strongest thing on this whole page for your stated priority: a player starting from Spa inherits nine hand-cut sky stops and a tuned bounce and edits from there, instead of starting from a colour picker and a green field.

Plumbing worth deciding now

The anti-cheat

verify.py's built(slug) does TRACKS.find(x => x.slug === slug) against a global array that jsrt pushes as one JSON blob of the entire pool at startup. Do not add user tracks to that — it grows without bound and every verification pays for it.

There is already a precedent for the right shape, in the same file: load_racing_line(slug) pushes one track's line on demand, explicitly because doing all of them for something only one caller wants is waste. A load_track(track) that appends a single dict to TRACKS is the same move, and it is a handful of lines.

Covers

Auto-framed by porting SCAN from tools/_hero.py to run in the browser the editor is already rendering in, with the author able to orbit and re-shoot. No Playwright per submission — which matters more than it looks, because the process that would run it is the single eventlet worker that also relays every live race pose at 30Hz.

The uncomfortable bit: pool covers stay server-rendered, so there are now two implementations of one framing, and your own note says the framing lives in one place on purpose because a cover and a share card once disagreed about where you stand. I'd accept it and pin it — a test that runs SCAN both ways on the same fourteen tracks and asserts the same window. It is the cheapest thing that stops the two drifting.

Guests

/make opens with no login and keeps one draft in localStorage; saving, sharing or submitting prompts a sign-in and attaches the draft to the account. In the CrazyGames build /make, the gallery and every Community shelf 404, the same way /login already does — the portal forbids a game offering its own login, and authorship without identity is not a thing.

My calls, stated

You didn't pick these, so I have. All of them are one-line changes if you disagree.

  • 20 drafts per account, 3 in the queue at once. Enough to keep several ideas going; not enough to flood you.
  • 400 moves and 6000 units per track. Big Red, the longest in the pool, is 3335.
  • Names: 32 characters, the nineteen reserved, a profanity filter on submit. The review gate catches the rest, and it is you.
  • Difficulty is the author's claim, overridable on your queue screen. It stays a label — nothing derives from it, exactly as now.
  • Medals are derived from the ribbon, always. tools/set_medals.py cuts from a board, and a user track's board is too small and too self-selected to cut from.
  • Rate limit on submit and on save, since both build a ribbon and one of them runs the checks.
  • User JavaScript runs in the sandbox and nowhere else. Interiors and terrain carving stay out of v1 as engine features, with reasons above — though code mode can now reach a good deal of both, which is rather the point of having it.
  • Scenery caps: 60 placements in data mode; 2,500 collider and 20,000 mesh triangles either way; 150KB baked.
  • No provider proxying, no hosted key, no exceptions. The chat panel is browser-to-provider or it does not ship.

Build order

Twelve phases, each one shippable and each one provable. The order is chosen so the riskiest thing is first and the UI is last.

1

Replayer, schema, chokepoint

The moves schema, replay(doc) → Builder, the drive_user_tracks table, and tracks.get() resolving a live row. No UI at all.

Proof: express each of the 14 tracks with no scenery.js as a moves document, replay it, and assert the ribbon is byte-identical to the folder's. tools/snapshot_tracks.py already exists to make exactly that comparison. If the schema can rebuild Sandy Cove and Big Red exactly, it can carry anything a player writes.

2

Read-only /make

Render a moves document: the list, the 3D world, the height strip. Nothing is editable and the five starting shapes are seeded rows.

Proof: the page draws all five, and Circuit closes.

3

Editing

Add, delete, reorder, and the inspector. Declarative width / edges / bank per move. Undo. Live rebuild on every change.

Proof: a rebuild stays under one frame on a 400-move track, and reordering never silently rewidens a later move.

4

Drive it

The Drive button hands the built track to the existing game.js in solo mode. This is the moment the editor becomes fun, and it should arrive early.

Proof: drive a draft that exists only in localStorage, with no account.

5

The palette editor

Every key, the driver's-seat preview, and the eight warnings. Fork-a-palette from any of the nineteen.

Proof: each warning fires on a case taken from track-defects.md, and none of them fires on any of the nineteen.

6

Scenery as data

The placement schema, the engine-owned props(ctx) interpreter, and the nine objects. Placement UI is a list beside the moves list, with the same at / side / off inspector.

Proof: express Spa's furniture, Silverstone's hangars, runways and both inside barriers, and Tokyo's towers as placement lists, and assert the collider triangle counts match the hand-written files. test_scenery.py already pins those counts.

7

Scenery in code, sandboxed

The sandboxed iframe and worker, the ctx surface, the bake, and the numbers validator with the KIND whitelist. The ctx helpers land on the five existing files in the same commit.

Proof: a deliberately hostile props — one that reads document.cookie, one that fetches /api/run, one that emits KIND.BOOST, one that loops forever — and all four are contained, named, and reported to the author.

8

Bring your own AI

The generated spec on the clipboard, paste-back errors, and the provider-picker chat panel with the key in localStorage. connect-src for three hosts on /make only.

Proof: the spec is generated from source and a test fails when ctx gains a name the spec does not mention. No request to any provider passes through the box.

9

Accounts, save, checks, submit

Sign-in attaches a draft. The check runner, the clean-lap requirement, the submit screen.

Proof: a deliberately broken track cannot be submitted, and the reason names the check.

10

Queue and approve

/admin/queue: names, one Drive button, approve / reject / note, difficulty override. The status machine and the ribbon hash.

Proof: a geometry edit on a live track wipes its board and re-queues it; a palette edit does not.

11

Gallery, shelf, covers, forking

/tracks, the Community row on the home page and in the switcher, in-browser SCAN covers with re-shoot, and Make my own.

Proof: the SCAN parity test on fourteen tracks; a fork of Spa arrives with Spa's sky and without its grandstands, and says so.

12

Rooms, verification, adoption

jsrt.load_track() for lazy QuickJS injection, rooms on user tracks, and tools/adopt_track.py to turn a row into a real tracks/<slug>/ folder when one earns it.

Proof: a top-3 lap on a user track is re-driven and accepted; an adopted folder passes the whole drive suite unchanged.

Left open

Three I'd rather you decided than I assumed, none of them blocking phase 1.

  • Does a cover regenerate when a palette changes? The shot is of the old sky otherwise, and nothing can detect a stale one — the same failure mode as shoot_tracks.py on the pool.
  • Do rooms on user tracks affect the same ELO as pool rooms? Approval gates it either way; separate ratings would be safer and one more number to explain.
  • What happens to a live track when its author deletes their account? Other people's records are on it.
